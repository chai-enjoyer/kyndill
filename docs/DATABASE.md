# Database

PostgreSQL 14+ schema for Kyndill, applied through versioned SQL migrations under `backend/db/migrations/`. Every schema change is a new numbered file; nothing is ever edited in place once it has been applied to a real environment.

## Conventions

- **UUID primary keys** generated by Postgres' built-in `gen_random_uuid()` (no `pgcrypto` extension required on Postgres 13+).
- **Foreign keys cascade on delete.** When a user is deleted, their pet, habits, completions, friendships, gifts, and notifications are removed with them.
- **TIMESTAMPTZ for instants, DATE for calendar days.** `habit_completions.completed_on` is a `DATE` (the day a habit was checked off in the user's local sense) while `completed_at` is a `TIMESTAMPTZ` (the precise moment it was recorded).
- **Check constraints over enums.** Enumerated values (visibility, species, category, rarity, etc.) use `CHECK (col IN (...))` rather than Postgres `ENUM` types so future values can be added without a migration that locks the table.

## Triggers

Both triggers live in `010_triggers.sql`.

### `trg_users_init_resources` (AFTER INSERT ON users)

Creates the default pet (`star` species, name `Kyndill`) and a corresponding `streaks` row for every new user. New streak rows start with two streak freezes. Runs `AFTER INSERT` because we need the user's PK to exist before we reference it.

### `trg_pets_update_stage` (BEFORE UPDATE OF total_habits_completed ON pets)

Keeps `pets.stage` in sync with `total_habits_completed`:

- `0..50` -> stage 1
- `51..200` -> stage 2
- `201+` -> stage 3

Fires `BEFORE UPDATE` so the trigger can mutate `NEW.stage` in place. An `AFTER UPDATE` trigger would have to re-issue an `UPDATE`, which would recurse onto itself. Behaviorally equivalent: by the time the row hits disk, `stage` reflects the new `total_habits_completed`.

## Indexes

`009_indexes.sql` covers:

- Every foreign-key column. Postgres does not auto-index FKs, and joins fall back to sequential scans without them.
- Time-ordered access patterns: `(user_id, completed_on DESC)` for habit history, `(user_id, completed_at DESC)` for focus sessions, `(user_id, is_read, created_at DESC)` for the unread-notifications query.
- Filtered lookups: active habits per user, incoming friend requests by status.

`UNIQUE` constraints (`users.email`, `users.username`, `items.name`, `pets.user_id`, etc.) automatically create their own lookup indexes; we do not add duplicates.

## Migration workflow

Apply with:

```bash
npm run migrate --workspace backend
```

`backend/db/migrate.ts` records every applied file in a `schema_migrations` table. Each file runs inside a transaction; a failure rolls back cleanly and the file stays unapplied. Files are discovered alphabetically and applied in order.

Add a new migration by creating the next numbered file (e.g. `012_xxx.sql`) and re-running the script.

## Design notes

### Streak fields are denormalized on `users`

`users.streak_current`, `users.streak_longest`, and `users.last_completion_date` mirror the corresponding columns on `streaks`. The spec required both. `streaks` is the source of truth (because `freeze_count` is only there, and updates happen with row-level locking on a single user-keyed row). The mirrored fields on `users` exist so a profile lookup can avoid a join. The application is responsible for writing both transactionally.

If this becomes a maintenance burden, the next migration should drop the mirrored columns and switch reads to a view that joins.

### Trigger direction differs from the literal spec

The spec asks for `AFTER UPDATE` on `pets.total_habits_completed`. We use `BEFORE UPDATE` so the trigger can write `NEW.stage` without recursion. Net effect is the same: by the time anyone observes the row, `stage` is correct.

### Friends store both directions

Inserting `(a, b)` and `(b, a)` doubles row count but lets every "my friends" query start with `WHERE user_id = $me`, indexed and direction-free. The alternative (`(min, max)` only) requires `OR` predicates and worse query plans. The app layer must keep the two rows in sync when accepting a friend request.

### JSONB for sparse, optional structure

`habits.days_of_week`, `notifications.metadata`, `activity_events.metadata`, and `users.notification_prefs` use JSONB. The shape is app-defined and small, and we don't expect to index inside the JSON. If query patterns develop around specific keys, a `CREATE INDEX ... USING GIN ((metadata -> 'foo'))` migration is the appropriate next step.
